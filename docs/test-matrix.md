# Matriz de testes mínimos do MVP

Auditoria da Fase 9 (issue #53, spec #10). Cada teste mínimo exigido em `docs/mvp-web-pwa.md` (seção "Testes mínimos") e nas histórias de usuário 1 e 2 da spec é mapeado para o teste existente que exercita o comportamento de verdade, nos seams acordados:

- Backend: API HTTP do NestJS contra PostgreSQL real (`packages/api/test/*.e2e-spec.ts`, vitest + supertest).
- Frontend: fluxos de UI com React Testing Library + MSW (`packages/web/test/*.test.tsx`).

Os testes foram lidos, não só localizados pelo nome: um teste só conta como cobertura quando exercita o comportamento (não basta mockar o resultado). Onde a leitura mostrou que nada cobria o comportamento, a lacuna foi coberta com um teste novo, marcado abaixo como **Lacuna coberta (nova)**.

Legenda da coluna Status:

- **Coberto**: já existia teste que exercita o comportamento.
- **Coberto + reforçado**: existia cobertura, e a auditoria acrescentou testes para casos que ela não alcançava.
- **Lacuna coberta (nova)**: nenhum teste cobria; o teste foi escrito na auditoria.
- **Coberto, com achado**: coberto, mas a leitura revelou um defeito registrado em "Achados da auditoria".

Convenção de referência: `arquivo` > `nome do teste`. Os arquivos de backend ficam em `packages/api/test/` e os de frontend em `packages/web/test/`.

## Achados da auditoria

Nenhum foi corrigido nesta fase (a fase não adiciona funcionalidades): ficam registrados aqui e devem virar tickets separados, ligados à spec #10.

### A1. Rotas de escrita de Usuários ignoram o escopo OWN (backend)

- Onde: `packages/api/src/users/users.controller.ts`. `GET /api/users` e `GET /api/users/:id` aplicam o escopo OWN; `PATCH /api/users/:id`, `POST /api/users/:id/deactivate`, `/reactivate`, `/reset-password` e `DELETE /api/users/:id` só checam a ação (EDIT, DELETE) e não olham `req.authScope`.
- Reprodução (verificada com um teste descartável): perfil customizado com `USUARIOS` = VIEW, EDIT e DELETE com escopo OWN edita (200), desativa (201) e exclui/anonimiza (200) outro usuário.
- Impacto: baixo na demo (o administrador tem escopo total e o perfil Cliente não recebe EDIT em Usuários), mas contradiz "permissões por módulo, ação e escopo" para um perfil que o administrador consegue montar pela própria matriz.
- Por isso não há teste automatizado para essa recusa: ele falharia hoje. Quando o ticket for feito, o teste esperado é "perfil com EDIT/DELETE em Usuários e escopo OWN recebe 403 OUT_OF_SCOPE ao alterar outro usuário", em `users.e2e-spec.ts`.

### A2. Matriz de permissões do perfil não é bloqueada visualmente sem a ação EDIT (frontend)

- Onde: `packages/web/src/pages/ProfileMatrix.tsx`. Os checkboxes, o seletor de escopo e o botão Salvar só se desabilitam para o perfil Administrador; a tela não consulta `can(PERFIS_DE_ACESSO, EDIT)`. Quem só visualiza perfis vê a matriz editável e recebe 403 da API ao salvar.
- Impacto: contraria o requisito "bloqueio visual de ações sem permissão". Os botões Novo perfil e Desativar/Reativar dessa mesma página já são bloqueados (e agora testados).

### A3. Tela de presença não é bloqueada visualmente sem a ação EXECUTE (frontend)

- Onde: `packages/web/src/pages/AttendancePage.tsx` (botões Presente e Faltou). A rota exige só o módulo Presença; a tela não consulta a ação EXECUTE. Quem só visualiza vê os botões habilitados; a API recusa (coberto em `attendance.e2e-spec.ts` > "recusa quem só pode ver a presença (sem a ação de executar)").
- Impacto: mesmo requisito do A2. O perfil Professor da demo tem EXECUTE, então a demonstração não é afetada.

## Resumo

- Testes mínimos de backend: 13 itens, todos mapeados a testes que exercitam o comportamento; 2 itens tiveram lacunas de concorrência cobertas (reserva/remarcação sob concorrência e duplicidade concorrente) e a edição de usuários foi reforçada.
- Fluxos mínimos de frontend: 11 itens, todos mapeados; a lacuna de bloqueio visual (Clientes, Usuários, Perfis, Templates/Modalidades e Agenda administrativa) foi coberta.
- Testes novos: 5 no backend em `reservations.e2e-spec.ts`, 4 no backend em `users.e2e-spec.ts`, 3 + 1 + 1 + 2 + 2 no frontend (`ClientsPage`, `UsersPage`, `ProfilesPage`, `TemplatesModalidadesPage`, `AgendaAdminPage`).
- Achados: 3 (A1 no backend, A2 e A3 no frontend), sem correção nesta fase.
